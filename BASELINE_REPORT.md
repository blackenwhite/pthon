# Baseline report

This is the RGB-D baseline at commit `405fee95`, recorded by `02d1929` (`step 0: freeze reproducible RGB-D baseline`) on the clouds already in `out/`. Numbers below are that freeze. A later rerun can change wall, opening, and polygon counts because Open3D’s floor RANSAC is unseeded. It should not start inventing a ceiling height.

Residuals in the JSON (`rmse_m`, `median_residual_m`) are plane-fit error, not tape-measure or laser accuracy.

## Inputs

Both folders are Record3D captures: `camera_matrix.csv`, `odometry.csv`, `imu.csv`, `rgb.mp4`, and `depth/` plus `confidence/` PNGs. Depth frames are 256×192 `uint16` millimetres. RGB is 1920×1440. Nothing here is a private room scan, and nothing is fused across folders.

## Pipeline

```text
Record3D folder
  → inspect (poses, intrinsics, depth samples)
  → subsample RGB-D + poses
  → metric point cloud (PLY)
  → voxel downsample
  → floor / ceiling: Open3D segment_plane
  → walls: orientation-constrained numpy RANSAC
  → XZ footprint (wall lines, or a hull fallback)
  → occupancy-gap openings
  → plan.json + plan.svg + preview_plan.png
```

Optional paths that do not change this geometry: pose-graph drift ablation, stills and a shortened video from `rgb.mp4`, and a reconstruction-health report with a short repair loop. The health report checks the outline, not physical damage in the room.

## Strengths

- A local Record3D folder becomes a metric cloud and a floor plane without a network call.
- Floor fit error is about 2 cm on both frozen clouds.
- The CLI writes a plan the README can open (`plan.json`, `plan.svg`, `preview_plan.png`).
- When no ceiling plane is found, `height_m` stays null. The code does not fill in a typical room height.
- Opening JSON says the width comes from occupancy bins, not a detected frame.
- Two captures are not fused. Ceiling height is only allowed from the capture being fitted.

## Failure modes

- Wall count is unstable. Open3D `segment_plane` has no seed, and the numpy wall sampler then runs on whatever points remain. The same `c00a170fe1` cloud produced 7 walls and then 6.
- Several vertical planes survive. The fitter can treat furniture or other vertical structure as a wall. That is why one room shows six or seven walls.
- The footprint is a fallback hull, not a clean room outline. On `c7d28f72c6` the polygon span (11.73 × 14.88 m) is larger than the camera path (about 8.3 × 9.1 m).
- The look-up capture still has no ceiling. The highest leftover horizontal plane was 0.64 m above the floor, so height stays blocked. The 2.86 m percentile figure is not a ceiling measurement.
- Openings are occupancy gaps. Kinds such as door and window are size heuristics.
- Each JSON describes one capture. There is no stitched property plan.

## Unsupported assignment requirements

This baseline does not implement:

- a photo tier or an RGB-only video tier that measures the room
- multi-room stitching
- physical or concealed damage segmentation
- scope line items
- a consumer-app comparison
- an iOS / TestFlight capture app
- accuracy against a tape or laser
- a result that is stable on an unseen room

Derived stills and a shortened video can be extracted from `rgb.mp4`. They do not measure the room.

## Claims this system does not make

- Fit RMSE is not room accuracy.
- `height_p95_minus_p05_m` is not ceiling height.
- A blocked ceiling is not “about 2.4 m”.
- Openings are not detected doors or windows.
- Six walls are not a verified room boundary.
- The polygon span is not a measured floor size when the hull fallback is in use.
- Drift JSON is an ablation of pose-graph versus raw odometry, not a claim that drift is removed.
- The reconstruction-health report is not a damage inspection of the building.
